# ADR-004: 注文・チケット購入スナップショット保持方式

## メタ情報

- ADR-ID: ADR-004
- タイトル: 注文・チケット購入スナップショット保持方式（明細テーブルへの購入時点データ埋め込み）
- ステータス: Accepted
- 日付: 2026-07-15
- 関連REQ-ID: FR-008, FR-010, C-DATA-004, DM-005, DM-007
- 関連チケット/PR: —

## 1. Context

- 背景: 注文確定時点の価格・商品名・数量・割引情報を保持する必要がある（C-DATA-004）。購入履歴（FR-010）では購入時点のスナップショットを表示する要件がある。
- 課題: 商品情報（Product）や価格は将来変更される可能性があるため、注文明細がProductテーブルを参照するだけでは過去の購入時価格を正確に再現できない。
- 制約: DBスキーマはDM-005（OrderItem）・DM-007（TicketPurchaseItem）で定義済み。

## 2. Decision

- 採用する決定事項: **注文明細（OrderItem）・チケット購入明細（TicketPurchaseItem）に購入時点のデータを非正規化して埋め込む**方式を採用する
- 適用範囲: 注文確定（FR-008）・チケット購入確定（FR-009）・購入履歴表示（FR-010）
- 実装方針:
  - **OrderItem** に以下を保持（注文確定時に Product から値をコピー）:
    - `product_snapshot_name` (VARCHAR) — 注文時の商品名
    - `unit_price` (INTEGER) — 注文時の税込単価
    - `quantity` (INTEGER)
    - `subtotal` (INTEGER) — `unit_price × quantity`
    - `product_id` (FK, nullable) — 商品が削除されても履歴は保持するためNULL許容
  - **TicketPurchaseItem** に以下を保持（チケット購入確定時に Screening/映画情報から値をコピー）:
    - `screening_id` (FK)
    - `ticket_type` (VARCHAR) — 例: "一般" / "学生" / "シニア"
    - `unit_price` (INTEGER)
    - `quantity` (INTEGER)
  - 購入履歴表示（FR-010）ではスナップショット値を直接参照し、Product/Screeningテーブルへの結合は補助的に行う

## 3. Alternatives

- 代替案A: **Productテーブルへ外部キー参照のみ保持し、購入時点のバージョンを別テーブルで管理**
  - 不採用理由: 価格履歴テーブルの追加とバージョン管理の複雑性が今回のスコープには過剰
- 代替案B: **注文時点データをJSON列で保持**
  - 不採用理由: 型安全性が失われ、検索・集計クエリが困難になる

## 4. Consequences

- 期待効果: 商品情報変更・削除後も購入履歴で正確な価格・商品名を表示できる（C-DATA-004達成）
- トレードオフ: データ重複が発生するが、EコマースではこのパターンがDB正規化より実用上優先される
- リスク: 明細への書き込み漏れが発生した場合に履歴が壊れる。注文確定サービスのユニットテストで必ず検証する

## 5. Traceability

- C-DATA-004 → OrderItem/TicketPurchaseItemへのスナップショット埋め込み
- FR-010 → 購入履歴表示でスナップショット値を直接参照
- DM-005 → OrderItem の `product_snapshot_name`, `unit_price` カラム
- DM-007 → TicketPurchaseItem の `ticket_type`, `unit_price` カラム

## 6. Open Questions

- OQ-004（解決）: チケット券種は `ticket_type` カラムに文字列で保持する。具体的な種類（一般/学生/シニア等）と価格はシードデータまたは別の設定テーブルで管理する。初期実装では "一般" 固定とし、複数券種はバックログとして扱う
