# ADR-002: 認証・セッション管理方式

## メタ情報

- ADR-ID: ADR-002
- タイトル: 認証・セッション管理方式（JWT + HttpOnly Cookie）
- ステータス: Accepted
- 日付: 2026-07-15
- 関連REQ-ID: FR-001, FR-002, C-AUTH-001〜004, ERR-002, NFR-SEC-001〜002, NFR-SEC-006
- 関連チケット/PR: —

## 1. Context

- 背景: ゲストと会員の権限分離、ログイン必須機能への未認証アクセス制御（C-AUTH-003）が必要。会員は自分のデータのみ参照可能（C-AUTH-004）。
- 課題: SPA + REST API 構成において、セッション管理方式を決定する必要がある。XSS・CSRF 対策も必須（NFR-SEC-005）。
- 制約: SPAはブラウザからAPIを呼び出す。サーバーサイドセッションストアは追加インフラを要する。

## 2. Decision

- 採用する決定事項: **JWT (JSON Web Token) を HttpOnly Cookie で発行・送受信する方式**を採用する
- 適用範囲: 全認証・認可処理
- 実装方針:
  - ログイン成功時にサーバーがJWTを生成し、`Set-Cookie: token=...; HttpOnly; SameSite=Strict; Secure` で発行
  - クライアントはCookieを自動送信するため、JavaScriptからトークンを読み取れない（XSS耐性）
  - JWTペイロード: `{ userId, email, iat, exp }` のみ（最小権限）
  - トークン有効期限: 24時間。リフレッシュは再ログインで対応（スコープ内では十分）
  - 認可ミドルウェア: Express ミドルウェアでJWT検証 → `req.user` にセット → コントローラで利用
  - 未認証アクセス時は HTTP 401 を返し、フロントがログイン画面へリダイレクト（C-AUTH-003）
  - 他会員データアクセス防止: サービス層でリソースの `user_id` と `req.user.userId` を照合（C-AUTH-004）
  - パスワードハッシュ: 別途 ADR-006 で決定

## 3. Alternatives

- 代替案A: **localStorage にJWTを保存**
  - 不採用理由: XSS攻撃でトークン窃取が可能。NFR-SEC-005に違反する
- 代替案B: **サーバーサイドセッション（express-session + Redis）**
  - 不採用理由: Redisなどセッションストアの追加インフラが必要でAzure構成が複雑化する
- 代替案C: **Azure AD B2C / 外部認証プロバイダー**
  - 不採用理由: 研究用サンプル（CON-001）であり過剰。内製実装でセキュリティ要件を満たせる

## 4. Consequences

- 期待効果: HttpOnly Cookieによりブラウザ上のJavaScriptからトークンが読み取れずXSSリスクを低減。SameSite=Strict でCSRF対策
- トレードオフ: トークン失効（強制ログアウト）のためにはサーバー側ブラックリストが必要だが、今回スコープでは24時間の自然失効で対応
- リスク: Cookie有効期限内にログアウト操作なしで端末を共有した場合のセッション引き継ぎリスク（ユーザビリティ上の注意事項として許容）

## 5. Traceability

- NFR-SEC-001 → パスワードハッシュ（ADR-006で別途決定）
- NFR-SEC-002 → 認可ミドルウェアで未認証アクセスを拒否
- NFR-SEC-003, C-AUTH-004 → サービス層の userId 照合で他会員データ保護
- NFR-SEC-006, ERR-002 → 認証失敗時は `"メールアドレスまたはパスワードが正しくありません"` の汎用メッセージを返す
