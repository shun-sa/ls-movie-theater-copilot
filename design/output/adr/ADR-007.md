# ADR-007: 注文ステータス遷移設計

## メタ情報

- ADR-ID: ADR-007
- タイトル: 注文ステータス遷移設計
- ステータス: Accepted
- 日付: 2026-07-15
- 関連REQ-ID: FR-008, FR-010, DM-005, CON-003
- 関連チケット/PR: —

## 1. Context

- 背景: 商品注文（FR-008）では注文確定後、配送処理（CON-003）までの状態管理が必要。注文ステータスの遷移定義がOQ-003として未確定だった。
- 課題: 購入履歴（FR-010）で注文状態を表示するため、ステータス値と遷移を明示的に定義する必要がある。
- 制約: CON-003により配送会社API連携なし。管理者側の注文ステータス更新まで（スコープ内）。今回は管理者UIは対象外のため、ステータス管理は最小限に留める。

## 2. Decision

- 採用する決定事項: **注文ステータスを4値（`pending_payment` → `confirmed` → `shipped` → `delivered`）+ `cancelled` で管理する**
- 適用範囲: 注文確定（FR-008）・購入履歴表示（FR-010）
- 実装方針:

  ```
  pending_payment  → confirmed → shipped → delivered
                               ↘ cancelled（任意の段階でキャンセル可、初期スコープでは未実装）
  ```

  | ステータス | 意味 | 遷移トリガー |
  |---|---|---|
  | `pending_payment` | 注文登録済・決済待ち | 注文確定API呼び出し時（模擬決済前） |
  | `confirmed` | 決済完了・注文確定 | 模擬決済成功直後（CON-002） |
  | `shipped` | 発送済み | 管理者操作（将来対応） |
  | `delivered` | 配達完了 | 管理者操作（将来対応） |
  | `cancelled` | キャンセル済み | 将来対応 |

  - **初期実装**: 模擬決済（CON-002）は常に成功するため、注文作成時に `confirmed` を直接セットし `pending_payment` をスキップしても可。ただし将来の本番決済連携を考慮し `pending_payment` を経由する設計とする
  - 購入履歴（FR-010）ではステータスを日本語ラベルに変換して表示する

## 3. Alternatives

- 代替案A: **`processing` / `completed` の2値のみ**
  - 不採用理由: 将来の本番移行時（配送会社API連携）に拡張が困難
- 代替案B: **注文ステータスを別テーブルで管理（ステータス履歴）**
  - 不採用理由: 今回のスコープでは注文履歴のステータス変更履歴の追跡は要件外。シンプルなカラム管理で十分

## 4. Consequences

- 期待効果: 将来の本番決済連携・配送API連携（OOS-001, OOS-009の解除）時に最小の変更で対応可能
- トレードオフ: `pending_payment` 状態が一瞬しか存在しないが、設計上は明示することで意図が明確になる
- リスク: なし

## 5. Traceability

- DM-005 → Order テーブルの `status` カラム（VARCHAR, NOT NULL）
- FR-008 → 注文確定時に `confirmed` をセット
- FR-010 → ステータスを購入履歴一覧・詳細で表示
- CON-002 → 模擬決済は常に成功するため `confirmed` が実質的な初期ステータス

## 6. Open Questions

- OQ-003（解決）: 注文ステータスを `pending_payment` / `confirmed` / `shipped` / `delivered` / `cancelled` の5値で定義する
