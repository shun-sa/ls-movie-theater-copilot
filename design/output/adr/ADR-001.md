# ADR-001: システムアーキテクチャ構成

## メタ情報

- ADR-ID: ADR-001
- タイトル: システムアーキテクチャ構成（フロント/バック分離 + REST API）
- ステータス: Accepted
- 日付: 2026-07-15
- 関連REQ-ID: AC-COM-001〜006, C-UI-001, NFR-PERF-001〜002, NFR-SEC-002〜005
- 関連チケット/PR: —

## 1. Context

- 背景: 映画作品閲覧・商品購入・チケット購入を一貫して提供するWebシステムを構築する。技術制約として TypeScript / React / Node.js / PostgreSQL / Azure が指定されている。
- 課題: フロントエンドとバックエンドの責務分離、API設計方針、DB接続方式をプロジェクト開始前に決定する必要がある。
- 制約: 言語=TypeScript、フロント=React、バック=Node.js、DB=PostgreSQL、クラウド=Azure

## 2. Decision

- 採用する決定事項: **SPA (React) + REST API (Node.js/Express) + PostgreSQL** の3層構成を採用する
- 適用範囲: システム全体
- 実装方針:
  - フロントエンド: React (Vite) + TypeScript。ページ単位でコンポーネントを分割
  - バックエンド: Node.js + Express + TypeScript。ルート → コントローラ → サービス → リポジトリの4層構造
  - DB: PostgreSQL。ORM は Prisma を採用（型安全なクエリとマイグレーション管理）
  - API形式: JSON REST API。エンドポイントは `/api/v1/` プレフィクスで統一
  - 認証: 別途 ADR-002 で決定
  - デプロイ: Azure App Service (バック) + Azure Static Web Apps (フロント) + Azure Database for PostgreSQL

## 3. Alternatives

- 代替案A: **Next.js によるフルスタック構成（SSR）**
  - 不採用理由: 技術制約で React + Node.js が明示されており、SSR の複雑性が今回のスコープには過剰
- 代替案B: **GraphQL API**
  - 不採用理由: クライアント数が1つ（SPA）であり、REST で十分。学習コストとツールセットの複雑化を避ける
- 代替案C: **モノリポなしの別リポジトリ分離**
  - 不採用理由: 小規模PJのため同一リポジトリで管理し開発効率を優先する

## 4. Consequences

- 期待効果: フロント/バック独立デプロイが可能。Prisma による型安全なDB操作でSQLインジェクションリスクを低減（NFR-SEC-005対応）
- トレードオフ: CORS 設定が必要。フロントとバックのAPI契約を明示的に管理する必要がある
- リスク: Prisma スキーマとDBマイグレーションの管理コストが発生する

## 5. Traceability

- NFR-SEC-004, NFR-SEC-005 → Prisma ORM 採用（パラメータバインディングによるSQLi防止）
- NFR-PERF-001〜002 → Express ミドルウェアによるレスポンス最適化で対応
- C-UI-001 → React コンポーネント設計で対応
